# Agent Build Scout — 2026-10-27

Five fresh agent projects, ranked by mechanism novelty, practical value, and hackathon potential. Performance figures below are maker-reported unless stated otherwise.

## 1. VFS-Bench — Same Agent Task, Two Tool Interfaces

**Original:** https://github.com/agentvfs/vfs-bench
**Official benchmark:** https://agentvfs.org/benchmark/vfs-bench-1
**Builder post (X mirror):** https://nitter.rdrama.net/qijia_shen
**Methodology review:** https://www.anchorterminal.com/tools/agentvfs

**What it does:** A fresh benchmark runs 200 agent tasks through two interfaces: ordinary MCP tools and AgentVFS, where connected services appear as files and actions as virtual command-line tools.

**Mechanism:** Each task runs through both arms with the same instruction, seeded service data, and evaluator. In the VFS arm, services such as email, Drive, Slack, GitHub, and Notion are described by VFS.md; the agent uses familiar shell operations such as ls, grep, jq, and pipes. The benchmark records task success and token use. The authors report 52% fewer tokens on average and pass@1 rising from 77.6% to 81.6%.

**Why it matters:** This tests the interface as a cause of agent performance. Instead of changing the model or adding more tools, it gives the model a terminal-shaped interface that matches skills learned during coding. It is a strong research-style hackathon because the result can be compared on identical tasks. A third-party review notes that the published run used one trial per arm and has not been independently reproduced.

**Hackathon adaptation:** Build a small virtual filesystem adapter for two services, such as GitHub issues and local notes. Run 30 fixed tasks through MCP and the filesystem interface with the same model. Reset data between runs and publish task-level success, token use, tool errors, and failed cases.

**Limitations:** The benchmark and its implementation are early-stage, and the authors produced the reported results themselves. One trial per task/model/arm is not enough to establish a general advantage. The average may hide large differences across models and task types.

**Flow:** 200 fixed tasks → Clone identical task state → MCP tool-call arm → Virtual FS + CLI arm → Same evaluator → Compare success + tokens

## 2. LayerFS — Ephemeral Workspaces, Durable Agent History

**Original:** https://github.com/Ephemeral-AI-Lab/layerfs
**LayerFS 1.1.0 release:** https://github.com/Ephemeral-AI-Lab/layerfs/releases/tag/v1.1.0
**Product demo video:** https://layerfs.ai/video/layerfs-v1.0.0-release.mp4
**Technical docs:** https://layerfs.ai/docs/

**What it does:** LayerFS gives each agent a disposable writable workspace over shared committed history. Agents can branch, test alternatives, rewind, and publish changes without cloning the complete working tree for every attempt.

**Mechanism:** Each filesystem-affecting tool call can mount a writable Workspace with its own copy-on-write overlay. Changes become immutable Commits in a SQLite-backed content-addressed Store. Content-addressed storage, content-defined chunking, and copy-on-write reuse unchanged data. Branches can fork from prior states; concurrent commits that change the same file are rejected as conflicts unless an explicit last-writer-wins rule applies. Unmount removes the temporary workspace but retains committed history.

**Why it matters:** This treats agent execution as branchable state, not as a stream of terminal text. Several workers can test different patches, keep the exact state that produced a result, discard failed branches, and promote a passing one. It builds on known filesystem methods, but applies them to agent tool calls and parallel exploration.

**Hackathon adaptation:** Build a smaller coding-agent runner with isolated worktrees or overlayfs. Give each worker a branch, run tests, save an immutable checkpoint, and let a controller promote only passing changes. Measure storage growth, startup time, and same-file conflicts against ordinary cloned worktrees.

**Limitations:** The project labels the current release a developer preview. Its README says it does not guarantee crash or power-loss durability. Managed FUSE needs Linux/WSL and elevated capabilities, and the container runtime is not a complete hostile-code security boundary. Do not use it as the only copy of important data.

**Flow:** Shared committed Store → Fork branch without full copy → Ephemeral writable Workspace → Agent tool call + tests → Commit changed data → Promote, rewind, or discard

## 3. PageSift — Memory-Bounded Web and Document Extraction for Agents

**Original:** https://github.com/YOLOW92/pagesift
**Project activity:** https://upstar.dev/r/YOLOW92/pagesift
**Oct 27 benchmark report:** https://github.com/YOLOW92/pagesift/blob/main/benchmarks/mix/results/report-2026-10-27.md

**What it does:** A new Rust extraction engine for agents and RAG pipelines converts websites, PDFs, office documents, e-books, RSS feeds, and archives into clean Markdown and structured data. It provides native SDKs and Firecrawl/Jina-compatible APIs.

**Mechanism:** PageSift combines a native Rust fetch-and-parse engine with memory-bounded processing, incremental collections, isolated HTTP sessions, and media/archive handling. The goal is to make extraction a predictable preprocessing stage before an agent reasons over the material. The repository publishes per-domain benchmark reports and raw results rather than only a single speed claim.

**Why it matters:** Agents often waste context on navigation chrome, repeated downloads, malformed files, and irrelevant page structure. A bounded extraction layer can reduce memory spikes and give the model cleaner evidence. The project is new and has active public development; its own benchmark suite makes the claims easier to inspect.

**Hackathon adaptation:** Build a research collector for 30 technical documentation sites and PDFs. Crawl incrementally, normalize results to Markdown, preserve URL/page provenance, and deduplicate assets. Evaluate evidence recall on 20 held-out questions while enforcing a fixed memory cap.

**Limitations:** The published benchmark numbers are maintainer-reported and have not been independently reproduced. Secondary project notes say dynamic rendering and DOM-repair tests are not best-in-class in every case. The repository uses AGPL-3.0 and lists a separate commercial license option.

**Flow:** URLs, PDFs, Office, RSS → Rust fetch + parse → Bounded incremental extraction → Markdown + structured records → Agent retrieves cited evidence

## 4. Phone-MCP — Real Android Control with a Separate Display

**Original:** https://github.com/Mirochill/Phone-MCP
**Conditional plans:** https://github.com/Mirochill/Phone-MCP/blob/main/docs/conditional-plans.md
**Verification and limits:** https://github.com/Mirochill/Phone-MCP/blob/main/docs/verification.md

**What it does:** Phone-MCP connects an AI client to a real Android phone. The agent can inspect app interfaces, tap, type, swipe, read or reply to notifications, transfer files, and install APKs. Its separate-display mode lets an agent work without always taking over the screen the person is using.

**Mechanism:** The Android companion connects outward to a personal relay over WebSocket; an MCP client uses HTTPS and OAuth to call tools. The system distinguishes foreground control from a separate virtual display, ties actions to recent snapshots, and returns fresh observations after actions. The repository also documents conditional plans that can branch on device state. The user starts and can stop each session; this is a device-control bridge, not a background model service.

**Why it matters:** Many mobile workflows have no stable public API. This provides an inspectable path to automate the real interface, while separate-display control reduces disruption to the human. The device and screenshots make a clear live demo.

**Hackathon adaptation:** Build a mobile QA agent for one Android app. Run it on a separate display, capture a snapshot after each action, and recover when a button moves or a dialog appears. Compare completion and recovery across ten UI perturbations against a fixed-coordinate script.

**Limitations:** It requires Android permissions and Shizuku for some separate-display and file features; device and app compatibility vary. The relay can see tool payloads and responses, so self-host it if that matters. The project does not independently judge whether a requested purchase, message, or deletion matches user intent.

**Flow:** Agent client + OAuth → Personal MCP relay → Android app over WebSocket → Accessibility / separate display → Fresh observation → Next action or recovery

## 5. veil — Reversible Secret Masking for Agent Debugging

**Original:** https://github.com/Sanexxxx777/veil
**Original Reddit post:** https://www.reddit.com/r/cicd/comments/1x6by6j/i_had_a_written_rule_that_agents_never_cat_env/
**Author's limitations and tests:** https://github.com/Sanexxxx777/veil

**What it does:** A one-file Python CLI masks known secrets in logs before an LLM or coding agent reads them, then restores the secrets in the response. It supports streamed replies and uses only the Python standard library.

**Mechanism:** The tool replaces recognized secrets with placeholders that include a type and a short HMAC-SHA256-derived identifier. The same value gets the same placeholder across runs, so the model can correlate repeated failures without seeing the real credential. A local, permission-restricted mapping allows unmask to restore values after the response arrives; the streaming parser handles chunk boundaries and some placeholder edits.

**Why it matters:** Ordinary redaction often breaks the links between log lines. Stable placeholders preserve those links while reducing the chance that a secret reaches the model provider. It is a small, concrete security layer that can sit in front of an existing debugging workflow.

**Hackathon adaptation:** Wrap a log-triage agent in a mask → model → unmask pipeline. Seed logs with known tokens and private keys. Measure detection recall, false positives, streaming correctness, and diagnostic accuracy against raw logs.

**Limitations:** The author says it has not been measured on a corpus of real logs. It misses unknown formats and personal data such as names, emails, and phone numbers; it can over-mask hashes. Unmasking can put a working secret into model-generated output, so review restored commands before execution.

**Flow:** Raw log → Local secret detector → Stable HMAC placeholders → LLM / coding agent → Local unmask → Human reviews restored output
